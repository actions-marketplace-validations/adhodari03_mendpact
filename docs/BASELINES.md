# Contract baseline lifecycle

A MendPact contract baseline is a reviewed `mendpact.scan.v1` artifact used to decide whether a
later MCP capability change is compatible. Capturing data and trusting it are separate operations:
a scan or Guard run creates a candidate, while `baseline promote` creates the committed baseline.
Projects created by `mendpact init` keep `mendpact/candidates/` locally ignored while leaving
`mendpact/baselines/` available for reviewed files.

## First baseline

Capture the target with the production policy generated by `mendpact init`:

```bash
mendpact scan https://api.example.com/mcp \
  --policy mendpact.toml \
  --output mendpact/candidates/candidate-scan.json
```

Inspect the candidate offline:

```bash
mendpact baseline inspect mendpact/candidates/candidate-scan.json
```

The output includes the scan ID, exact target, capture time, scan status, canonical SHA-256, MCP
protocol version, and capability counts. Inspection returns `0` for a complete passing scan, `1`
for a complete scan that failed its policy threshold, and `2` for an invalid or incomplete
artifact.

After reviewing the JSON findings and capabilities, copy the printed scan ID into the promotion
command:

```bash
mendpact baseline promote \
  mendpact/candidates/candidate-scan.json \
  mendpact/baselines/baseline-scan.json \
  --accept-scan-id "paste-the-reviewed-scan-id" \
  --expected-target https://api.example.com/mcp
```

Commit the promoted baseline in its own reviewed change. Do not commit access tokens, temporary
candidate reports, or unrelated local output.

## Updating a baseline

Guard can retain the current scan with `--save-scan`, and the GitHub Action exposes the equivalent
`save-scan` input. Download that candidate, inspect it, and review the contract diff before
promotion. Replacing an existing baseline requires a separate flag:

```bash
mendpact baseline promote \
  mendpact/candidates/candidate-scan.json \
  mendpact/baselines/baseline-scan.json \
  --accept-scan-id "paste-the-reviewed-scan-id" \
  --expected-target https://api.example.com/mcp \
  --replace
```

`--replace` acknowledges only the destination replacement. It does not bypass scan-ID or target
matching.

## Failed scans

A failed scan can still contain a complete contract, but it also means a deterministic finding
reached the scan's policy threshold. Promotion therefore stops unless the reviewer adds the
independent `--accept-failed-scan` flag. Prefer fixing the finding or approving a narrow, expiring
policy waiver before capture. If promotion is intentional, retain the reason in the pull request.

Error scans, missing graphs, target/graph mismatches, non-MCP graphs, duplicate nodes or edges,
dangling edges, status/finding threshold inconsistencies, and artifacts without exactly one server
node cannot be promoted.

## File safety and reproducibility

Promotion refuses to overwrite an existing file without `--replace`, refuses symlink destinations,
requires an existing real destination directory, canonicalizes the validated report, and uses an
atomic same-directory replacement. The canonical digest is formatting-independent, so equivalent
compact and pretty-printed candidates produce the same review identity.

Baseline inspection and promotion are entirely offline. They do not connect to the MCP target,
execute a tool, contact a model provider, load a bearer token, or incur provider cost.
